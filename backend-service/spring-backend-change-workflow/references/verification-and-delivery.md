# 验证证据与交付

## 高风险变更的六阶段通过条件

用于主入口识别出的高风险任务。六阶段是本技能裁剪后的协作方法，不是行业认证标准；材料可合并，通过条件不能用阶段名称代替证据。

| 检查点 | 通过条件 |
| --- | --- |
| Brainstorm：需求 | 触发条件、预期行为、范围和验收口径明确；不存在未确认且会改变结果的业务或协议假设 |
| Design：设计 | 职责、数据流、信任边界、接口兼容、事务/异步边界、失败恢复及观察点明确 |
| Plan：计划 | 按可独立验收、审查和回退的行为切片，列出正常、边界和异常判据及外部依赖 |
| Execute：实现 | 保护已有修改；最小修改并执行与切片匹配的检查，审查实际差异 |
| Verify：验证 | 分别审查工程/安全约束和原始需求；测试不能只复述实现假设 |
| Ship：交付 | 关联变更与证据，明确限制和恢复条件；真实发布仍须在用户授权范围内 |

## 从真实配置选择入口

- 读取目标构建文件、Wrapper 配置与 CI，确认 JDK、Maven/Gradle、模块依赖和 profile。不从另一个项目复制版本或构建命令。
- Maven `validate` 只检查项目模型；离线成功不证明所有编译/测试依赖都已缓存。多模块选定目标时检查是否需要一并构建依赖模块。
- 核查 `maven.test.skip`、`skipTests`、Surefire/Failsafe、标签/分组/排除规则及命令行覆盖。必须读取实际执行数、失败数和跳过数，不能把零测试或示例标签测试视为业务覆盖。
- Maven 构建 profile 与 Spring 运行 profile 分别核实；资源过滤可能将构建属性写入运行配置。项目配置和示例 Compose 不代表当前服务监听与凭据。
- 文档变更检查内容、相对链接、编码及差异；新文件尚未受跟踪时另行检查，不能只依赖默认 `git diff`。

## 选能证明问题的最小测试

| 要证明的行为 | 优先入口 | 需防止的误判 |
| --- | --- | --- |
| 纯业务计算、帧解析、状态转换 | 调用生产逻辑的单元测试 | 不在测试中另写一个相同实现；不必加载完整 Spring 上下文 |
| 请求校验、序列化、错误响应和授权 | 项目已有 Web 层测试及必要安全配置 | 关闭过滤器或完全 Mock 授权后，不能声称验证了真实权限 |
| SQL、映射、约束、并发更新及事务 | 对应 ORM 的持久层/组件测试，必要时使用隔离的实际数据库 | Mock Mapper 不证明 SQL 和事务；JPA 测试切片不能直接代表 MyBatis |
| 缓存、异步及事务代理语义 | 经 Spring 容器真实 Bean 调用的针对性测试 | `new Service()` 或 Mock 掉代理不能证明注解生效；纯逻辑测试仍可不启容器 |
| 跨组件数据流与消息状态关联 | 必要的应用集成测试和隔离外部依赖 | 不默认接入共享服务、启动真实定时任务或发送设备指令 |

按项目实际 Boot/JDK 与依赖选择可用注解和测试 API；不为套用示例升级框架。复用已有测试设施，只有行为确实需要时才引入容器或新依赖。覆盖率和用例数量不设通用固定门槛，以所改正常、边界和错误恢复行为的有效断言为准。

Maven 集成测试还需检查 Failsafe 是否实际绑定到生命周期；只有 `pluginManagement` 配置或只有 `*IT` 文件不代表测试被执行。根据真实绑定选择生命周期阶段，并核对报告；不能假定执行一次 `test` 已覆盖全部集成测试。

## 证据层级

| 层级 | 可以支持的结论 | 尚不能支持的结论 |
| --- | --- | --- |
| 源码/静态审查 | 指定数据流、边界及受检查规则 | 运行时并发、服务可用和设备执行 |
| 编译/打包 | 当前目标和工具链下产物可生成 | 测试已执行、运行配置正确 |
| 单元/组件测试 | 当前生产逻辑在所述模型内的行为 | 外部服务、Broker、真实设备完整行为 |
| 服务启动/API 集成 | 指定环境的启动及已调用路径 | 所有权限/异常路径或设备执行 |
| Broker/双端联调 | 已观测的传输、解析与应答 | 无证据的设备物理动作或长期稳定性 |
| 设备验收 | 指定设备、版本与条件下的执行结果 | 所有硬件版本、网络条件和故障均已覆盖 |

对可复现缺陷，优先验证原逻辑失败、修复后通过；覆盖正常、边界与错误恢复。测试应调用真实生产代码，不能在测试中重写同一实现再互相证明。没有环境或工具时保留限制及建议验证方式，不虚构通过。

## 安全实践参考

以下参考与六阶段组织方法是不同维度；只按任务选适用项，不默认要求项目获得某种认证。

- [NIST SP 800-218 SSDF v1.1](https://csrc.nist.gov/pubs/sp/800/218/final)：用于安全需求、代码/构建保护、设计与代码审查、测试及漏洞根因处置的参考；先复用现有检查入口，不把建议写成已部署能力。
- [OWASP ASVS 5.0.0](https://asvs.owasp.org/)：用于 Web/API 安全需求与技术控制验证。重点按变更检查服务端输入、身份认证、对象级授权、敏感数据及错误/日志处理；引用具体条目时核实原文并标明版本。
- 查询/命令构造采用参数绑定或合适的安全 API；无法绑定的动态标识符核查允许列表。敏感日志脱敏；异常不直接暴露凭据或内部堆栈。
- 新增或升级依赖时核实来源、兼容性和已知漏洞，沿用版本管理；依赖扫描、静态分析等只有实际运行后才能报告结果，未经要求不搭建整套新平台。

这些版本是编写时选用的参考基线。任务要求采用最新标准或合规等级时，再查询官方发布并明确目标版本、适用范围与验收要求，不自动声称已符合全部条款。

## 服务器操作与风险确认

- 所有服务器操作均以不影响服务器及现有服务正常运行为前提。排查优先采用低开销、限定范围的只读方式；只读操作也需评估 CPU、内存、磁盘 I/O、网络和数据库锁等影响，不以“不修改文件”作为无风险依据。
- 操作可能影响可用性、性能、数据完整性或安全时，先向用户说明具体命令/操作、目标和影响范围、风险后果以及恢复措施；必要时给出低风险替代方案，取得明确确认后执行。包括重启/停止、配置或网络变更、升级部署、迁移清理，以及高负载扫描、备份和压力测试等。
- 风险不明时先收集足以判断的低开销信息；仍无法评估时暂停相关操作并说明未知项。确认前不执行有风险命令、不预先启动后台任务；备份或预检查本身有风险时也适用此规则。
- “检查、修复、直接做”等笼统要求不能替代具体风险确认。风险已说明且用户已确认的同一操作无需重复询问；新增目标、扩大范围或发现新风险时重新说明并确认。已授权且无新增风险的低开销检查可继续；Git 推送另按[风险告知后的再次确认](git-delivery.md#推送前再次确认)执行。

## 交付与实际发布

交付说明关联需求、变更、实际命令/报告、环境和未解决事项；纯文档或小改无需长报告。公共契约变化同步权威接口/协议文档。

只有用户授权实际发布且完成上述必要风险确认后才执行发布操作：核对源码版本、构建环境、配置、迁移脚本和部署目标，按风险记录产物摘要；准备恢复条件并观察健康状态和关键业务路径。不要为证明技能或代码有效而写入生产数据库、发布镜像或触发真实设备。

提交分组、工作区保护及推送前再次确认统一见 [Git 交付规则](git-delivery.md)，不将提交、推送与部署授权互相替代。
