# Git 交付规则

适用于本技能支持的后端变更；目标仓库的分支、远程地址、产物路径和实际 CI 条件在执行时核实，不从其他项目复制。

## 授权与工作区保护

- 未经用户明确要求，不创建 Commit、不推送、不发布部署、不执行数据库迁移/清理或改变真实设备持久状态。提交、推送和部署是不同操作，授权不能互相替代。
- 先查看工作区和暂存区，再按目的区分本次与用户已有修改；只暂存相关内容，检查实际暂存差异和清单，不能使用整个目录或 `git add .` 夹带无关内容。
- 用户已有暂存内容应原样保留且不夹带提交；无法隔离时说明具体冲突，不能重置或覆盖用户工作来制造干净状态。禁止用破坏性命令丢弃已有修改。
- 生成的编译/打包产物、日志、测试报告、本地 IDE 配置、凭据和环境文件不纳入提交；Wrapper、测试资源或仓库明确管理的必要文件按项目约定处理，不按后缀一刀切。

## 按目的确定提交粒度

先审查实际差异，按可独立审查、验证和回退的单一目的分组，再决定一次还是多次提交。目录和模块不是分组依据；分组是否独立无法确定时，先说明分组再提交。

- 同一功能/缺陷必需的 Controller、Service、Mapper/XML、DTO/BO/VO、调用方、测试和最小文档保持一起；迁移脚本与依赖它的数据格式/接口变更不能被机械拆开。
- 多模块中同一 API、协议或序列化契约的声明、实现和必要调用方保持一致，避免产生中间不可编译、不可运行或契约不一致的提交。
- 独立功能、另一缺陷、无关重构/格式化及另一主题文档分别组织；各自须可独立说明和回退。已有无关修改继续留在工作区，不因“同一次会话”而合并。
- 用一句中文说清提交的唯一目的；若必须用“以及”连接两个独立目的，应拆分。标题简洁明确，正文说明内容、原因、影响、验证与未验证项；对 API/协议、数据格式或部署变更补充兼容依据和恢复条件。
- 涉及多仓库时各自形成可审查提交，说明契约对应与验证关系；不能用一个仓库的构建结果证明另一个已通过。

## 推送前再次确认

**用户明确说“推送”后，仍需先告知本次风险并再次取得明确确认；确认前不执行推送。** 文档提交或低风险判断不能免除这一步，也不能用试推送触发远端检查来替代确认。

先准备具体、可审查的说明：

1. 远程仓库、源/目标分支及本次全部待推送提交，包括此前已提交但尚未上传的内容；普通分支推送不是按本次暂存文件筛选。
2. CI/CD、Webhook 或服务端钩子可能导致的构建、部署、服务重启、资源占用或数据操作。仅核对仓库 CI 文件不能证明服务端没有其他自动化；未知项明确保留，不能承诺零影响。
3. 提交可见范围、敏感内容泄露风险，以及分支更新或历史改写的后果；不擅自强制推送。推送不能自动撤回信息传播，回退提交也不代表已执行部署或数据变化已恢复。

先用本地可得信息核对；远程状态未刷新时标明记录可能过时，不必为了准备风险说明就先连接生产服务器。获准进行的远程只读核查仍遵循服务器运行保护规则。

风险说明后等待用户确认，不能将先前的一般推送要求或沉默当作确认。确认后仅执行所说明范围；目标、提交集合或风险发生变化时重新告知并确认。拒绝非快进等异常不构成强推、重写历史或自动扩大范围的授权。

## 发布与设备操作

实际发布、迁移、数据修复或设备操作需确认目标环境/设备、产物或脚本、影响范围及恢复方式，执行服务器风险确认要求；不能假定应用回退即可恢复已迁移数据。若任务还涉及固件下载、烧录、Flash 擦写或量产工具，另核实目标设备、固件文件及可回退方式，不由后端代码修改授权推导执行权限。
