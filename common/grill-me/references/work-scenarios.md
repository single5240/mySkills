# 工作场景与追问示例

以下是选择问题的线索，不是必须逐项执行的清单。不要把示例中的假设写成当前项目事实。

## 嵌入式与设备协议

优先沿“输入 → 接收/采集 → 缓冲 → 状态机 → 输出/存储”追一条路径。

- ISR、DMA、主循环或任务之间谁拥有数据，何时发布，谁可修改？是否需要原子性或同步？
- 缓冲区容量与最坏处理延迟是否匹配？溢出、短帧、粘包、重复帧如何处理？
- DMA 地址、生命周期和对齐是否满足目标芯片约束？只有芯片具有相关 Cache 时追问一致性；不套用固定对齐值。
- 超时是否考虑无符号 Tick 回绕？错误后能否退出等待、释放资源并进入可恢复状态？
- 参数保存的写入频率、掉电窗口、擦写停顿和磨损是否影响既有实时任务？
- 先确认原工具链、板卡及协议依据，再讨论实现。缺手册或原理图时保留未知，不猜寄存器或电气特性。
- 不默认添加重复校验、双重状态归属、动态分配或复杂框架；让每项保护对应一个具体失效场景。

例：用户说“我要用片内 Flash 保存设置”。先问：
“断电时，设置需要保留到哪一个时间点？我建议先以‘用户确认保存后必须保留’为标准；是否还需要自动保存，会直接影响写入频率和存储设计。”
后续根据回答再选写入频率、掉电提交或擦写停顿中的一项，不一次全问。

## Web、小程序与设备联调

优先沿“设备帧 → BLE/串口接收 → JS 会话状态 → HTTP → Java 服务 → 数据库 → 历史展示”或当前项目实际链路展开，不假定这些环节都存在。

- 谁决定开始、停止、完成？用户退出、断连和超时后，设备状态与页面状态如何收束？
- 异步回调是否可能迟到或乱序？重复采样、重试上传由哪一层去重？
- 前端展示权限与服务端资源鉴权分别在哪执行？记录归属来自什么可信身份？
- 数据库提交、缓存更新和消息发送失败后，如何识别与恢复不一致？
- 用一条实际数据解释 Promise、async/await、Java 接口或事务；仅在当前问题需要时补 SQL、框架和语法。
- 明确 Mock、类型检查、真实后端、真实设备分别能证明什么，不把页面能打开视为整条链路通过。

例：用户说“小程序停止训练后上传记录”。先问：
“哪一个事件才算本次训练结束？如果协议支持停止应答，我建议以设备确认停止作为正常结束依据，并把断连保留为异常结束；目前协议是否提供这种应答？”
先查协议能否回答最后的事实问题，查得到就改为询问用户对异常结束记录的业务取舍。

## 理解自测示例

用户说“考考我有没有看懂这个 BLE 会话模块”。先读实际代码，选择一条真实存在的路径，再问：
“页面退出后，如果上一会话的采样回调才到达，当前实现会如何处理它？”

等回答后按代码判定。若实现没有会话隔离，明确解释实际后果；不要以理想设计替代当前实现，也不要未经请求开始修复。
