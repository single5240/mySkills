# 技术决策笔记

只记录能帮助后来维护者作判断的信息，篇幅与决定的复杂度相称。

## 1. 判断是否值得写

用户明确要求时记录；否则，仅在有长期价值且现有代码、测试、文档未充分表达时记录，例如：

- 看似多余的实现实际受兼容性、硬件、资源或并发约束限制。
- 选型、模块职责或数据格式的取舍，后来维护者很可能重新讨论。
- 已验证的失败路线，以及什么条件变化后可以重试。

改了行为、涉及多个文件或改动量大，本身不构成写笔记的理由。

## 2. 先查，再写

1. 读取宿主项目规则，沿用已有 ADR、设计文档或决策记录位置；按主题、模块和机制名检索相关记录。搜索隐藏目录时使用 `rg --hidden`。
2. 已有记录负责同一决定时，就地更新路径、参数等仍属同一理由的事实；无需重复建篇。
3. 决定或核心理由改变时，写新记录并与旧记录互链，旧记录注明已被取代；保留仍有价值的旧理由。历史记录不作为当前行为的依据，核对实际源码。
4. 没有惯例时，使用 `docs/decisions/YYYY-MM-DD-topic.md`，目录按需创建，不额外建立分类树或总索引。

沿用用户已有授权；只有未决取舍或宿主规则要求时才提问，不为写笔记增加确认步骤。已作出的决定可直接记录，不必补走提案流程。

## 3. 最小内容

沿用项目格式；没有格式时参考以下骨架，短决定每节一两句即可：

```markdown
# <决定主题>
状态：待定 / 已采用 / 已否决 / 已取代（选择实际状态）

## 背景与约束
什么问题需要决定，哪些事实限制了选择。

## 决定与理由
选择什么，为什么适合这些约束；待定事项明确写为待定。

## 考虑过的其他方案
仅列真实考虑过的方案：优势是什么，为什么未采用。没有则写明未比较，不凑数量。

## 影响与验证
收益、代价、适用边界；实际验证的命令或证据、结果及未验证项。
```

只写可核实的事实和决策理由，不复述聊天或代码流程，不编造备选、测量值或通过结论。取舍依赖条件时，说明何种变化值得重访。

涉及嵌入式、RTOS 或驱动时，按实际风险记录：ISR/任务所有权与同步；DMA 对齐、Cache 与内存分配限制；超时和错误清理。硬件结论注明板卡、工具链及依据，区分主机测试、目标构建与实板验证，未验证项保留为缺口。

## 4. 写后核对

- 对照源码及已有记录，确认状态、路径、参数和引用有效；计划不写成已实现事实。
- 核对理由、代价和验证证据是否足以帮助下一位维护者；删去重复内容。
- 有项目文档检查入口则运行相关检查；没有则检查 Markdown 链接和 `git diff --check`。只有文档变化时，无需重跑固件或全量测试。

随实现同步记录实际结果，交付时给出笔记路径及关键验证缺口；遵循宿主提交规则，不因记录笔记自动提交或推送。
