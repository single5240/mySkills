# 嵌入式固件研发六阶段工作流 (Embedded Six-Stage Workflow)

本技能提炼自实战嵌入式工程规范（N32G455 / STM32 / 8位机等量产固件项目），通过 `Brainstorm → Design → Plan → Execute → Verify → Ship` 六道质量门禁（Gate）控制硬件与固件开发风险。

---

## 1. 任务风险分级（决定流程裁剪深度）

六阶段是检查点，不要求机械填写六份材料。每个阶段都要约束行为、持久材料和通过条件。已确认事实写入需求条目、设计说明、任务清单、Diff 和验证记录，不依赖聊天。假设、编译成功或自述完成不能当作通过。依据或验证不成立时退回对应阶段；用户要求直接执行可减少形式材料，但不能跳过硬件依据、关键安全决策、工作区保护与验证真实性。已有明确授权无需重复询问。

涉及代码精简、分层、校验位置、资源预算、时钟树、存储恢复或交付分组时，按需读取 [最小实现与交付约束](./references/implementation-constraints.md)。具体芯片配置、项目路径和验证命令留在项目权威文档。

- **低风险小改**：目标明确、不涉及硬件时序、对外协议或跨模块共享状态时，简化为：`调查事实 → 最小修改 → 编译/静态检查 → 汇报`。
- **普通功能**：完成需求边界确认、简短设计、可独立验收的垂直任务切片、实现验证与交付说明。
- **高风险改动**：涉及 **中断(ISR)、DMA、并发竞态、系统/外设时钟、看门狗、无线/总线通信协议、Flash/EEPROM 擦写、校准、掉电恢复、电源、低功耗唤醒、安全电平、启动文件/链接脚本或芯片厂商库** 时，必须完整执行以下六阶段 Gate，并逐项核对 [硬件与并发安全检查清单](./references/hardware-safety-checklist.md)。

---

## 2. 六阶段门禁（Stage Gates）

### Stage 1: Brainstorm（需求澄清与依据核查）
- **事实自查 vs 用户决策**：源码、工程文件（`.uvprojx`/`.scw`/`CMakeLists.txt`）、已有文档和 `git status` 能回答的事实由 Agent 自行检索；产品行为、风险接受、硬件取舍、兼容策略、存储格式和没有依据的默认值提交用户确认，并给出推荐、依据和影响。
- **决策顺序**：有依赖的决策沿关系逐项确认。沿用项目里已有的稳定需求 ID，不在聊天或临时文档里改写成另一套事实源。漏答不能当成默认答案。
- **提示词缺失反馈（最多 3 项）**：当缺少芯片型号、原理图/引脚连接、协议定义或数据手册依据时，最多列出 **3 个最关键缺失信息**，说明原因并给出可复制的补充提示词。
- **Gate 通过条件**：目标、范围、明确不做项和验收口径一致；会改变硬件行为、数据格式或用户体验的取舍已有结论。未通过不进入正式实现。关键决策未关闭时可以继续只读调查或原型，不能固化相关产品策略。

### Stage 2: Design（方案设计）
- **分层边界**：说明需求如何进入现有分层和中断转发，而不是只改当前文件。沿用目标项目现有层次；如采用 `APP`/`DRV`，应用负责业务/状态机/UI，通过驱动访问硬件，驱动负责协议/时序/超时恢复。不得借流程新建未经批准的目录，也不得把这些目录名强加给其他工程。
- **复杂任务还须写明**：责任与调用方向、状态所有权、接口变化、共享状态与原子性、超时及错误恢复、兼容或降级、资源预算、验证入口、明确不做项和回退方式。
- **高风险设计必含项**：
  - **DMA/中断**：通道归属、抢占优先级关系、缓冲区所有权与生命周期、启动/完成/超时取消路径，以及与现有高优先级采集的关系。
  - **Flash/EEPROM**：数据版本、边界与校验、写入原子性、磨损评估、掉电中断与启动恢复策略。上述策略未确认前不得进入擦写实现。
- **长期决策**：难以回退且会长期影响模块边界、协议、时钟或存储格式的结论写入对应权威文档。临时实现细节不扩散为长期规范。
- **Gate 通过条件**：模块职责、数据流/时序、异常恢复路径和验证观察点明确，且有数据手册/原理图依据。依据不足时退回需求澄清或请求资料。

### Stage 3: Plan（垂直切片规划）
- **垂直切片**：按“可独立演示或验证的行为”拆分小任务。每个任务写明目标、范围、前置依赖、明确不做项、验收标准、验证方式和失败回退点。重构只有在当前功能无法安全落地时才作为独立前置任务，不把顺手重构或格式化混入功能切片。
- **主机回归计划**：按键、状态机、协议、算法或存储恢复等可脱离硬件验证的修改，按需使用 [embedded-host-regression](../embedded-host-regression/SKILL.md) 选择相关已有测试、故障模型及必要新增用例；纯文档或无逻辑变化的小改不因此新增测试。项目具体命令留在项目 AGENTS.md／测试文档。
- **验收判据**：使用“给定……当……那么……”描述正常、边界与异常场景；硬件任务写明需观测的引脚、波形、频率或寄存器。
- **Gate 通过条件**：每个任务都能独立回答“怎样算完成”，并有可执行或可操作的验证入口。不能独立验收的任务继续拆分。

### Stage 4: Execute（最小实现与短反馈循环）
- **工作区保护**：动手前检查 `git status --short`，保护用户已有改动；保持原文件编码（UTF-8 或历史 GBK）与换行符，不擅自更换编译器版本或重构厂商驱动库。
- **范围**：只实施已确认的需求、设计和当前切片，不按聊天印象扩大范围。
- **短反馈闭环**：`读取切片 → 确认验证入口 → 最小修改 → 立即构建/检查 → 审查 Diff`。当前切片没有新证据前，不推进依赖它的下一片。
- **验证入口先于修改**：纯算法、状态机、换算、CRC 和参数校验在条件允许时先建立会失败的测试或固定输入输出。寄存器、DMA、时序和界面改用编译、契约、调试计数或仪器观察。
- **退回**：失败反复指向需求假设或模块边界时，退回 Brainstorm 或 Design，不在执行层持续堆补丁。
- **切片收尾**：检查改动范围、错误路径、资源增量，以及与前序切片的回归。未经要求不提交、不推送、不烧录、不擦写。
- **Gate 通过条件**：完成最小实现，取得与当前切片风险匹配的新证据；编译或静态检查不能单独关闭硬件时序、并发及掉电风险，缺少的验证明确保留。

### Stage 5: Verify（双维独立审查）
- **Standards Review（规范审查）**：对照 [硬件与并发安全检查清单](./references/hardware-safety-checklist.md) 和 [最小实现与交付约束](./references/implementation-constraints.md) 检查分层、实时性、资源增量、并发、超时、编码、厂商代码和提交范围。
- **Spec Review（需求审查）**：从原始需求与协议定义反查正常、边界（如数组首尾、通道边界、计数器回绕）与异常恢复路径。实现者的测试可能与实现共享误解，高风险改动要独立复查数据流和控制流。
- **证据范围**：优先复用现有测试，覆盖需求、新缺陷或关键边界。相关检查通过后，只有新修改、新失败或未解决风险才扩大验证。测试数量不是质量指标。
- **主机回归证据**：执行计划中相关回归，确认读取当前生产源码并记录命令、结果和模型范围；可复现的缺陷尽量检查旧逻辑失败、修复后通过。主机逻辑不能替代原工具链构建及实板验证，断言数不是固定门槛或设备数，细节按需查阅 [主机回归技能](../embedded-host-regression/SKILL.md)。
- **诚实报告验证层级**：严格区分 **静态审查 / 原工具链编译 / 仿真或主机回归 / 上板实测 / 示波器与逻辑分析仪验证 / 掉电注入**。未执行的层级必须明确标注“未验证”及建议测试方法。这几层不能互相代替，编译通过不能证明时序、电气、DMA 竞态、掉电恢复或产品规则。

### Stage 6: Ship（交付与文档同步）
- **交付报告**：包含修改内容与原因、影响范围、对协议/时序/存储/资源占用的影响、已执行的验证结果、未验证项、剩余风险、回退方式，以及要同步的权威文档。
- **交接**：跨会话说明当前目标、已完成项、关键决策所在位置、下一步和阻塞条件。引用现有需求、设计、Diff 和验证记录，不复制第二份事实源。只有会长期影响工程判断的结论才写回长期规范。工作完成不等于提交、推送、烧录或擦写授权。
- **测试报告**：功能／版本交付或用户要求时，按需采用 [主机回归报告方法](../embedded-host-regression/references/test-reporting.md)，关联实际被测源码、用例、执行证据与遗留问题；自动汇总事实，人工确认验收结论，不为每次小改强制生成长报告。
- **Git 提交规范**：仅在用户明确要求时创建 Commit。按“可独立审查、独立回退的单一目的”划分提交粒度；使用简洁明确的中文标题（如 `修复DMX短帧发布条件`），排除 `Objects/`、`*.hex`、`*.axf`、`*.map` 等构建产物。
