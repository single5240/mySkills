# 测试报告与执行记录

## 使用条件与标准参考

日常局部迭代保留机器执行记录即可；功能完成、重要缺陷修复、版本交付或用户要求时，按范围生成可阅读报告。纯文档修改不需要制造固件测试报告，报告长度随风险裁剪。

测试计划／用例在执行前确定输入、预期和通过条件；执行记录保存实际命令与输出；报告汇总本次证据、偏差、缺陷和验证边界，三者不能互相替代。

参考 [GB/T 38634.3—2020](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=ECB3501CEC6DE54D1D5A23B820D34F0F) 和 [ISO/IEC/IEEE 29119-3:2021](https://www.iso.org/standard/79429.html)。它们是不同版本的标准文件；本技能提供工程简化模板，不是逐条标准转录，也不自动声明符合标准。正式符合性按客户／组织指定版本和实际条款核对。

## 内容与统计

按需裁剪 [报告模板](../assets/test-report-template.md)，保留：

- 被测源码和测试脚本身份：实际路径、Commit、未提交状态、源码／宏／配置哈希。执行后才创建的 Commit 不能自动视为被测版本。
- 需求／缺陷依据、目标、实际纳入的生产模块及未覆盖调用上下文。
- 环境、完整命令、输入、故障模型、实际结果与证据；主机替身、目标构建和真实设备分开说明。
- 遗留问题、限制与下一步验证。没有计划用例清单时，不反推“覆盖全部需求”。

| 状态 | 含义 |
| --- | --- |
| PASS | 已执行，实际满足预期 |
| FAIL | 已执行，实际不满足预期 |
| BLOCKED | 构建、环境或前置条件阻止测试完成 |
| NOT RUN | 未执行，或记录不足以确认结果 |
| N/A | 不适用，注明原因 |

每条用例用稳定 ID 关联需求，记录前提／输入、预期、实际、状态和日志；不把预期直接复制成执行证据。编译失败不能写成运行通过，失败后未开始的组仍是 NOT RUN。用例数、测试组数、断言数和设备数分别统计，未知数量不能填 0。

故意引错预期触发断言失败，“预期失败被检出”属于敏感性检查通过，不是产品缺陷；保留原始返回码。编译失败、崩溃或超时不能冒充成功检出业务断言。

## 自动事实与人工结论

`scripts/run_examples.py` 在新证据目录生成 `summary.json`、阶段日志和自动执行摘要 `report.md`，仅报告两个教学测试组及可选负向检查，不是产品验收报告。

同类摘要可以单独转换：

```text
python scripts/report_summary.py /path/to/summary.json --output /path/to/new-report.md
```

输入采用示例运行器结构：顶层 `cases`，每组含 `name`、显式 `status`、`steps`、源码哈希及可选 `mutation.status`。它不是兼容所有测试框架的解析器；缺失状态显示 NOT RUN，不从 PASS 字符串猜结果。

修改报告逻辑时运行 `python scripts/test_reports.py --cc /absolute/path/to/compiler`。该检查在独立临时副本注入编译错误和断言错误，验证 PASS／FAIL／BLOCKED／NOT RUN、负向检查结果、缺失记录处理和报告不覆盖已有文件；不修改技能原示例。

自动报告只填时间、环境、命令、返回码、源码身份和证据。需求覆盖、缺陷影响、目标构建、硬件验证和发布建议留给人工确认；不能自动生成“无遗留问题”或“可量产”。

开发期可使用临时目录；长期报告若进入 `docs/test-reports/`，必要日志／JSON应同时归档到可访问的 CI 或交付附件。仅保留个人临时路径不能支撑长期追溯。相对证据链接应相对报告位置计算。

原始日志和可执行文件通常不入 Git，摘要和必要用例按项目规则保存。归档前按对象处理用户名、机器路径、私有协议、设备标识和凭据，不无条件上传整个工作目录。
