# AGENTS.md 质量约束化 (From Process Orchestration to Quality Constraints)

## 1. 适用范围与背景

- **技术方向**：`common`
- **使用范围 (Scope)**：`global`
- **来源**：Junsen，《[别再教聪明模型做小学数学：从「过程编排」到「质量约束」的 Agent 范式演进](https://junsen.online/blog/%E5%88%AB%E5%86%8D%E6%95%99%E8%81%AA%E6%98%8E%E6%A8%A1%E5%9E%8B%E5%81%9A%E5%B0%8F%E5%AD%A6%E6%95%B0%E5%AD%A6%E4%BB%8E%E6%B5%81%E7%A8%8B%E9%A9%B1%E5%8A%A8%E5%88%B0%E4%BB%A3%E7%A0%81%E8%B4%A8%E9%87%8F%E9%A9%B1%E5%8A%A8%E7%9A%84agent%E8%8C%83%E5%BC%8F%E6%BC%94%E8%BF%9B/)》，2026-10-17。
  - 原文全文：[references/from-process-to-quality-constraints.md](./references/from-process-to-quality-constraints.md)
  - 作者的 AGENTS.md 模板（原文第八节，未改动）：[examples/AGENTS.quality-constraints.md](./examples/AGENTS.quality-constraints.md)
- **与其他技能的关系**：[`embedded-six-stage-workflow`](../embedded-six-stage-workflow/SKILL.md) 负责高风险硬件改动的门禁；本技能负责判断哪些流程该保留、哪些该改成工具检查或删除。

核心观点（详见原文）：

1. 工作流是在补偿模型当时的能力，模型变强后，重流程会挤占上下文，并诱导 Agent 优化“完成阶段”而不是“系统恢复正确”。
2. 与其规定 Agent 每一步怎么做，不如写清楚什么不能破坏、什么条件必须满足、什么证据才算完成。
3. 能机器验证的规则交给类型系统、lint、测试和 CI；AGENTS.md 只做“工程地图”。
4. 调查只要求建立“最小充分系统模型”，不要求扫描全部代码。
5. 人只介入高风险、不可逆或需要业务判断的决策，而不是审批每一步。

## 2. 核心执行流程

若任务是把现有 AGENTS.md 整理进技能库，先按 [技能提炼与项目事实分离](./references/extract-to-skills.md) 判断去向；默认保留源文件，只将可复用内容合并到已有技能，不把整理任务扩展为固件改造。

1. **先调查仓库事实，再读 AGENTS.md**：
   - 列出已有的测试、验证脚本、CI 配置、构建命令和工具链安装情况。
   - 逐条核对 AGENTS.md 中的“当前事实”（例如“没有命令行构建脚本”“编译器版本”）与仓库是否一致；不一致的先记录，作为最高优先级修正项。
2. **给每条规则分类**：

   | 类别 | 判据 | 处理 |
   | :--- | :--- | :--- |
   | 可机器验证 | grep、`git diff`、编译器、测试、map 文件能给出确定结论 | 迁移为检查脚本或 CI；AGENTS.md 只留一句约束加入口命令 |
   | 不可机检的不变量 | 影响正确性，但只能靠设计、审查或仪器证明 | 保留，写成“不能破坏什么 / 完成需要什么证据” |
   | 风险升级 | 不可逆、跨模块、公共契约、需要产品决策 | 保留为显式清单，写明需要用户确认的条件 |
   | 过程编排 | 规定步骤顺序、阶段输出格式、模板填写 | 低风险任务删除；高风险任务压缩为通过条件 |
   | 重复事实 | 同一事实在 AGENTS.md 多处或与权威文档重复 | 只保留一处，其余改为指针 |

3. **补“验证入口表”**：每个入口写明命令、覆盖范围、依赖和**不能证明什么**，防止 Agent 把仿真通过写成实测通过。表中每条命令必须当场实际运行过才能写入。
4. **补“调查停止标准”**：能解释问题如何发生、根因在哪、影响哪些调用方与共享状态、修改边界落在哪里时，即可停止扩大检索；出现新证据再继续。
5. **保留风险分级与确认等级**：可逆、局部、低风险的改动自主完成；影响较大但行为明确的，先说明影响再执行；高风险、不可逆或涉及业务的，先确认。
6. **分批落地**：先修事实错误和验证入口（低风险、收益高），再做规则检查脚本，最后才精简流程章节；每批都请用户确认范围。

## 3. 嵌入式固件项目的适配边界

原文作者也承认，强审计和不可逆场景仍需要明确流程。嵌入式项目中以下内容**不得**按“轻流程”精简：

- [ ] **硬件依据**：引脚、寄存器复用、时序、电平无数据手册或原理图依据时禁止猜测。
- [ ] **不可机检的风险**：ISR/DMA 竞态、时钟树、看门狗窗口、掉电恢复、Flash/EEPROM 擦写，保留设计确认和分级验证。
- [ ] **不可逆操作**：烧录、整片擦除、修改目标板持久化数据，始终需要用户授权。
- [ ] **验证层级诚实**：静态审查 / 编译 / 仿真 / 上板 / 示波器或逻辑分析仪 / 断电注入分开报告。
- [ ] **工具链现实**：要求的编译器（如 ARMCC 5）在当前机器未安装时，如实标为未验证，不用替代编译器结果冒充。

适合迁移为机器检查的典型嵌入式规则：

| 文字规则 | 机器检查方式 |
| :--- | :--- |
| 应用层不直接操作外设库 | `APP/*.c` 不得包含芯片外设头文件（历史例外列白名单） |
| 驱动层不依赖应用层 | `DRV/*` 中不得出现 `#include "app_` |
| 厂商代码原则上不改 | `git diff --name-only` 命中厂商目录即报警 |
| 只在主循环喂狗 | 喂狗函数调用点只允许出现在主循环文件 |
| 共享中断只在一处配置 | 全仓 grep 该 IRQ 配置调用，命中位置唯一 |
| 不提交构建产物 | 暂存区不得出现 `Objects/`、`*.hex`、`*.axf`、`*.map` |
| 不得新增编译警告 / 检查 RAM 增量 | 命令行构建（如 `UV4.exe -j0 -r <proj> -t <target> -o build.log`）后解析警告数与 `.map` 中 Code/RO/RW/ZI，与基线比较，见 [`keil-armcc-build-analyzer`](../keil-armcc-build-analyzer/SKILL.md) |
| 新增文本使用 UTF-8 | 对改动文件逐个尝试 UTF-8 解码 |

## 4. 验证与交付

1. **事实可追溯**：AGENTS.md 中每条“当前配置/当前事实”都能追溯到源码、工程文件、脚本或实测记录。
2. **命令可执行**：验证入口表中的命令全部实际运行，记录结果；依赖缺失时写明缺什么、怎么补，而不是删掉条目。
3. **差异检查**：执行 `git diff --check`，确认没有整文件换行符或编码变化；运行脚本产生的缓存（如 `__pycache__/`）在交付前清除。
4. **交付说明**：列出修正的事实错误、迁移为工具检查的规则、删除或压缩的流程段落、未执行的验证及原因。
