# Vue 管理后台改动工作流

技术方向：`common`；使用范围：`global`。适合 Vue 3、TypeScript、Vite 管理端，包括 Element Plus / Pinia / Vue Router 及 RuoYi / plus-ui 派生工程。先确认真实技术栈，不向其他工程强加这些依赖或目录。

## 建立最小充分的工程模型

读取工作区规则、`git status --short`、包脚本与锁文件、目标模块及最近似实现，确认包管理器、实际安装版本、自动导入、请求和样式约定。已有修改必须保留；用户要求仅分析时保持只读。

沿目标行为追踪“页面/组件 → hook/store → API → 请求封装 → 代理/后端”，只读实际涉及的路径。能解释触发条件、数据和状态归属、受影响调用方、修改边界与验收方法后停止扩大检索。工程事实自行查证；只有缺失的关键契约、产品行为或真实环境条件才询问用户。

| 当前任务                                 | 按需读取                                                      |
| ---------------------------------------- | ------------------------------------------------------------- |
| 列表、表单、弹窗、轮询、响应式或共享状态 | [状态与接口检查](references/state-and-contracts.md)的相关小节 |
| 登录、权限、动态路由、请求拦截或设备控制 | 同上文档的权限或设备小节，并核对调用方                        |
| 代理/接口异常、构建失败或缺陷            | 先按下一节定位，再读取相关状态检查                            |
| 验证、交付或工程规则整理                 | [验证与交付](references/verification-and-delivery.md)         |

具体 CRUD 模板、类型入口和页面壳沿用目标项目技能（如存在 `frontend-crud-coding`）；无需安装其他技能才能执行本工作流。来源笔记与评估用例仅维护技能时读取。

## 缺陷：按证据缩小范围

保留错误原文、最短复现、实际请求/响应和近期相关差异，敏感数据脱敏。对照同仓库正常路径，每轮提出一个可证伪假设，用最小观测区分原因，确认后再改；不能复现时标明未知项，补针对性观测，避免叠加猜测性配置、延时或重试。

502 按浏览器请求 URL、运行 mode、代理匹配/重写、目标监听和后端响应逐层定位，不把重启前端或关闭 CORS 当作通用修复。接口空白页需区分网络失败、业务码、响应结构、渲染异常及权限结果。修复无效或假设被否定时回查边界，不在同一假设上持续堆补丁。

## 按影响裁剪检查点

- **局部低风险**：文案、文档或行为明确的局部样式，事实核对、最小修改、针对性检查即可。
- **普通功能**：说明输入/输出、API 与权限契约、正常/边界/失败场景，按可独立验证和回退的用户行为切片实现，不按“先重构所有公共层”拆任务。
- **高影响**：认证授权、共享请求层、动态路由、公共状态、加解密、设备指令、全局主题、依赖主版本或构建环境变更，满足[六阶段通过条件](references/verification-and-delivery.md#高影响变更的六阶段通过条件)。检查点不要求六份文档、频繁 Commit 或逐步审批；明确授权不重复询问。

不猜测未定义的业务行为或破坏性契约；真实设备命令、生产数据写入及发布须在授权范围内。影响较大但行为已明确的改动，先说明影响后继续实现，不因技能形式要求停工。

## 服务器操作的前置条件

涉及服务器的排查、验证或维护，均以不影响服务器及现有服务正常运行为前提。先核实目标环境、影响范围与资源开销，优先采用低负载、只读检查；只读或可回退不等于没有运行风险。

存在或无法排除运行风险时，执行前必须说明具体操作、受影响的服务或数据、可能后果及恢复/回退方案，并取得用户明确确认。确认前仅继续不影响运行的调查；“直接做”不免除风险说明与确认。已有确认只覆盖原操作范围和已说明的风险，范围或风险扩大时重新确认。

执行中发现风险扩大或服务异常，停止后续操作并说明情况，按已确认的恢复方案处理。具体操作检查见[服务器影响评估](references/verification-and-delivery.md#服务器影响评估)。本节约束开发任务中涉及的服务器操作，不扩大本技能为独立生产部署技能。

## 实现时守住的边界

- 延续当前架构、API 形状和公共组件约定；不将错误修复扩展为重构、全仓格式化或依赖升级。不为降低 lint / 类型错误而关闭规则、滥用 `any` 或移除异常保护。
- 校验放在掌握信息的边界；页面校验改善交互，服务端授权和数据校验仍是权威。公共封装变更必须检查调用方，避免在每页复制相同补丁。
- 状态有明确所有者；派生数据优先计算，副作用与清理成对；慢请求不能覆盖新状态，旧请求的 `finally` 也不能清除新请求的 loading。
- 保留错误、取消、重复点击和卸载路径；写操作不自动无限重试。不要把 HTTP 请求成功写成设备执行完成。
- 组件拆分以职责、复用或隔离复杂度为依据；单一开关可留本地，不规定文件长度或强制把每个页面抽成 controller。

## 完成判据

按需要证明的行为选验证，核对实际命令、退出码、执行范围与结果。Vite 打包、完整类型检查、lint、浏览器交互、后端联调、设备实测分别报告；零用例、Mock 或旧构建结果不能冒充当前业务通过。

已有失败与新增失败分开说明，不能以“基线失败”为由省略相关检查，也不顺手修复无关问题。通过且最终修改未影响的检查不机械重跑；缺少工具或环境时说明未验证范围及补验方法。

交付简述修改与原因、影响、验证证据及遗留风险；只有明确要求才提交/推送。项目路径、端口、API、版本与故障快照留在项目文档，不能沉淀为跨工程常量。

### Git 提交与推送

提交、推送、发布及真实数据/设备写入分别授权。用户要求提交时，先检查工作区与暂存区差异，按可独立审查和回退的单一目的分组，只暂存相关改动；同一功能的页面、API/types、必要调用方、测试和说明保持完整，独立主题分开，用户无关修改留在工作区。依赖与锁文件配套提交，排除构建产物、缓存、报告、IDE 用户配置和秘密。中文标题明确唯一目的，正文记录原因、影响、验证及未验证项，涉及契约或外部行为时说明兼容与回退。

推送是“已有授权不重复询问”的例外：即使用户已明确要求推送，也先说明目标仓库/分支、待推送提交、CI / Webhook / 自动部署等可能后果及未知项，再取得一次明确确认后执行。对已告知并确认的同一次推送不循环询问；范围或风险变化时重新确认。推送请求本身不能替代这次风险确认。详细分组与推送检查见[Git 交付边界](references/verification-and-delivery.md#git-交付边界)。
