# 验证与交付

## 高影响变更的六阶段通过条件

| 检查点 | 通过条件                                                       |
| ------ | -------------------------------------------------------------- |
| 需求   | 触发条件、期望结果、范围和验收一致；未定义的业务取舍已确认     |
| 设计   | 数据流、状态归属、API/权限契约、失败恢复、调用方和兼容影响清楚 |
| 计划   | 切片按可验证行为组织；知道修改文件、正常/异常场景及回退边界    |
| 实现   | 最小改动；保留用户工作区和关键保护，无无关重构                 |
| 验证   | 相关静态、类型、构建和运行证据与结论一致；残留风险明确         |
| 交付   | 解释最终行为、影响、验证及未验证项；外部写入与发布符合授权     |

这是完成条件，不是固定长文档模板。普通任务可在简短说明和实际检查中满足。

## 按变更选择证据

| 改动                   | 优先证据                                                       | 限制                               |
| ---------------------- | -------------------------------------------------------------- | ---------------------------------- |
| 文档、技能、规则       | 内容、相对链接、元数据、差异检查                               | 无需为此启动业务服务或重跑产品构建 |
| 局部样式 / 交互        | 相关 lint / 格式检查，浏览器操作与必要视口/主题检查            | 截图不证明提交或权限逻辑           |
| API / 状态 / 组件逻辑  | 相关 lint、Vue 类型检查、已有相关回归；按导入和集成影响构建    | 静态工具不能证明接口在线           |
| 认证 / 公共封装 / 路由 | 调用方审查、类型与构建、登录/失效/无权限等关键路径             | 本地 Mock 不证明后端授权           |
| 构建 / 依赖 / 环境     | 锁文件与配置审查、实际目标 mode 构建，必要时启动和资源路径检查 | 开发模式正常不证明生产部署路径正确 |
| 设备控制               | 交互与状态验证、后端联调；授权条件具备才做设备验收             | 请求受理不等于设备执行             |

命令从目标 `package.json`、锁文件、CI 与已有测试读取；先确认脚本是否带 `--fix` 或全仓写入。Windows 下 `.ps1` shim 被策略阻止时优先 `.cmd`，不改变系统策略。不要机械套用 pnpm、oxlint 或 vue-tsc 到未安装它们的工程。

如仓库使用 Vue / Vite：确认构建脚本是否同时运行类型检查；单独 `vite build` 不等于完整类型检查。核对 Vitest 是否有配置、真实测试及执行数量，不能把“有依赖”或允许零测试退出当作回归覆盖。

有可复现逻辑缺陷时优先使用已有设施补正常、边界和失败用例，按需比较旧逻辑失败与修复通过。并发缺陷可控制两次 Promise 的完成顺序，验证结果及 loading 归属；取消测试检查无多余提示及状态污染。不要为无逻辑小改搭建新测试框架，也不写仅镜像实现的断言。

浏览器验证使用可用工具与测试账号，记录实际路由、步骤、预期与观察结果。缺少环境或凭据时明确未验证，不虚构截图或交互结果，不擅自创建账号及真实业务数据。

## 服务器影响评估

服务器操作应在执行前评估运行影响，不能为了取得验证证据而影响现有服务。先明确环境、服务依赖、操作对象和资源上限；无法判断时补充调查，不按“无风险”处理。

- 重启/停止服务、重建容器、覆盖部署文件、更新依赖、修改网络/防火墙、变更数据库及清理数据，检查停机、连接中断、数据损失与恢复风险。
- 压测、全盘扫描、大批量查询、日志遍历及批量下载，即使只读，也可能消耗 CPU、内存、磁盘或带宽；优先缩小时间范围、采样或限制数量。仍可能影响运行时先说明并确认。
- 风险说明需包含具体操作、受影响服务/数据、可能后果、恢复或回退方案；不可恢复的后果须直说。取得针对这些风险的明确确认后才能执行，不能用一般性的“排查一下”或“直接做”代替风险确认。
- 已确认的操作在原范围与已说明的风险内无需重复询问；新发现的风险或范围变化须重新确认。执行中服务异常时停止后续动作、说明现状，按已确认方案恢复，不自行扩大为重启或清理。

## 完成前核实

确认检查针对最终文件和正确 mode；记录关键退出码、错误范围和遗留项。区分本次新增失败、既有失败及环境阻塞。需要时以安全隔离的基线复现支持归因；不能覆盖用户修改来取得基线。

修复后检查原始需求，而非只检查报错消失；审查最终 diff 和新增文件，保护锁文件、生成声明、IDE 配置和用户已有改动。通过且未受后续编辑影响的检查无需反复执行。

交付保持简短：改了什么及原因、哪些场景有证据、哪些仍待验、公共变更如何回退。回退代码不代表能撤销已执行设备命令或业务写入。提交/推送遵循明确指令，中文标题及详细正文遵循目标仓库约定。
